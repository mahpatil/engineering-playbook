# Software Supply Chain Security

Standards for proving a container image's origin and refusing to run unverified ones.

> **Current Scope:** container images only. Dependency pinning, lockfiles, and language-package supply chain controls are  out of scope for now and will be covered by a separate standard.

## What is supply chain security?

It is the set of controls that tie a running image back to a known source commit and build, and that block images that lack that proof. The core pieces are vulnerability scanning, image signing, build provenance, and deploy-time enforcement.

## Why it's required

- **Integrity:** Prove the image is what the pipeline built, unchanged.
- **Traceability:** Link any running image to its commit, builder, and dependencies.
- **Early defense:** Known vulnerabilities fail the build, not production.
- **Auditability:** Evidence is generated by the pipeline rather than collected by hand.

## Who it's for

Security and platform teams set policy, and application teams produce the evidence in their pipelines.

---

## Principles

1. **Bind evidence to the digest.** Signatures and attestations attach to an immutable image digest, never a mutable tag.
2. **Prefer keyless, short-lived signing.** Long-lived signing keys in CI secrets are a theft and rotation risk. Federated identity (OIDC) that issues short-lived certificates solves this. When keyless isn't possible, use a managed key service with rotation.
3. **Enforce at runtime.** Pipeline checks can be bypassed; the cluster admits only images that verify. Fail closed.
4. **Generate evidence in a trusted build.** Provenance comes from the builder, not from the code being built.

## Pipeline

Build once, then scan, push, sign, attest, and admit:

1. **Build** from a clean, pinned source revision on a minimal base image.
2. **Scan** for vulnerabilities and fail the build above an agreed severity (a starting point is any fixable high or critical finding). Exceptions are time-limited, recorded with an owner, and reviewed before they expire.
3. **Push** the image to the registry and record its digest.
4. **Sign** the image digest.
5. **Attest** build provenance, and optionally an SBOM, and store them with the image in the registry.
6. **Admit** only verified images: an admission policy checks the signature and provenance before a pod starts. The policy pins the expected signer identity (the OIDC issuer and the repository or workflow that built the image), so a valid signature from any other identity is rejected.

Images already running are rescanned on a schedule, and new critical findings alert the owning team. A documented break-glass path lets a named group bypass admission in an emergency; every bypass is logged, time-limited, and reviewed afterward.

## Choosing tools

The controls above are what the standard requires; the tools below are examples.

| Control | Examples | Choose by |
|---|---|---|
| Vulnerability scan | Trivy, Grype, a registry's built-in scanner | Language and OS coverage, existing platform |
| Signing | Sigstore Cosign (keyless), a cloud KMS-backed signer | Whether OIDC federation is available |
| Provenance | SLSA (Supply-chain Levels for Software Artifact) provenance from a hosted builder | Build platform; aim for the highest SLSA level it supports |
| Admission | Kyverno, OPA Gatekeeper, a cloud's binary authorization | Policy language the team already uses |

## Rolling out enforcement

Start in audit mode in lower environments for a trial period (two weeks is a reasonable start — long enough to cover a typical sprint and image refresh cadence - although could be longer based on current estate) to find unsigned sidecars and third-party images. Move to enforce mode in production once the audit is clean. Decide upfront how to handle third-party images, for example by mirroring and signing them internally.

## Checklist

- [ ] Images are referenced by digest, not tag.
- [ ] Scan gate fails the build on agreed findings.
- [ ] Signature recorded for every release image.
- [ ] Provenance attached and verifiable.
- [ ] Admission policy enforces verification in production.
- [ ] Review third-party images and agree on approach.
