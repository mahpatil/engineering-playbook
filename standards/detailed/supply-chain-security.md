# Software Supply Chain Security

Standards for proving where a container image came from and refusing to run anything unverified.

## What is supply chain security?

It is the set of controls that tie a running image back to a known source commit and build, and that block images which lack that proof. The core pieces are vulnerability scanning, image signing, build provenance and enforcement at deploy time.

## Why it's required

- **Integrity:** Prove the image is what the pipeline built, unchanged.
- **Traceability:** Link any running image to its commit, builder and dependencies.
- **Early defence:** Known vulnerabilities fail the build, not production.
- **Auditability:** Evidence is generated by the pipeline rather than collected by hand.

## Who it's for

Security and platform teams who set policy, and application teams whose pipelines produce the evidence.

---

## Principles

1. **Bind evidence to the digest.** Signatures and attestations attach to an immutable image digest, never a mutable tag.
2. **Prefer keyless, short-lived signing.** Long-lived signing keys in CI secrets are a theft and rotation risk. Federated identity (OIDC) issuing short-lived certificates avoids them. Where keyless is not possible, use a managed key service with rotation.
3. **Enforce at runtime.** Pipeline checks can be bypassed; the cluster admits only images that verify. Fail closed.
4. **Generate evidence in a trusted build.** Provenance comes from the builder, not from the code being built.

## Pipeline

Build once, then scan, sign, attest, push and enforce:

1. **Build** from a clean, pinned source revision on a minimal base image.
2. **Scan** for vulnerabilities and fail the build above an agreed severity (a starting point is any fixable high or critical finding).
3. **Sign** the image digest.
4. **Attest** build provenance, and optionally an SBOM, and store both with the image in the registry.
5. **Admit** only verified images: an admission policy checks the signature and provenance before a pod starts.

## Choosing tools

The controls above are what the standard requires; the tools are examples.

| Control | Examples | Choose by |
|---|---|---|
| Vulnerability scan | Trivy, Grype, a registry's built-in scanner | Language and OS coverage, existing platform |
| Signing | Sigstore Cosign (keyless), a cloud KMS-backed signer | Whether OIDC federation is available |
| Provenance | SLSA provenance from a hosted builder | Build platform; aim for the highest SLSA level it supports |
| Admission | Kyverno, OPA Gatekeeper, a cloud's binary authorization | Policy language the team already uses |

## Rolling out enforcement

Start in audit mode in lower environments for a trial period (two weeks is a reasonable start) to find unsigned sidecars and third-party images. Move to enforce mode in production once the audit is clean. Decide upfront how third-party images are handled, for example by mirroring and signing them internally.

## Checklist

- [ ] Images are referenced by digest, not tag.
- [ ] Scan gate fails the build on agreed findings.
- [ ] Signature recorded for every release image.
- [ ] Provenance attached and verifiable.
- [ ] Admission policy enforces verification in production.
- [ ] Base image is minimal and runs as non-root.
