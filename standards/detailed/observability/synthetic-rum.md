# Synthetic Monitoring & RUM (Real User Monitoring)

Standards for **synthetic (active) monitoring** and **frontend / real-user (UX) analytics**. Together they cover the two halves of the UX perimeter: *active* checks that run regardless of visitor traffic, and *passive* collection of what real users actually experience.

---

## Why Synthetic + RUM

| | **Synthetic (proactive/active)** | **RUM (real-user/passive)** |
|-|----------------------------------|------------------------------|
| Traffic | Generated by the checker | Real end-user browsers |
| Coverage | Every journey, every hour, even in the dead of night | Only where users actually go |
| Detect | Outages BEFORE users see them | What users really experienced |
| Blind spot | Doesn't see real-user nuances, auth, geography spread is limited | Misses journeys nobody visits |
| Use for | Alerting/uptime SLAs, pre-release checks | UX analytics, performance budgets, DORA-style user metrics |

**Standard:** ship **both** — synthetic for availability + alerting, RUM for real-world UX analytics and performance budgets.

---

## Synthetic Monitoring

Synthetic checks are **scripted requests** that continuously verify availability and behavior from defined regions/geographies.

### Types
| Type | Checks | Use for |
|------|--------|---------|
| **API / HTTP checks** | HTTP status, latency, JSON assertions | Critical endpoints, APIs, uptime SLAs |
| **Browser checks** | Scripted multi-step UI flow (login → action → verify) | Critical user journeys, end-to-end flows |
| **Multi-step/transaction** | Sequence with state | Checkout, onboarding, high-value flows |

### Regions & scheduling
- Run from **≥2 regions** (and at least one region outside origin cloud) to detect region-specific issues.
- Critical API checks: **every 1 minute**; browser checks: **every 5–15 minutes**.
- Run on a schedule that matches your SLA (e.g., 99.95% availability → checks ≤ the downtime window you want to catch).

### Synthetic checks as code
```yaml
# synthetic/check.yaml
apiVersion: synthetics/v1
kind: ApiCheck
metadata:
  name: checkout-api-health
spec:
  service: order-api
  method: GET
  url: https://api.example.com/health/ready
  expectedStatus: 200
  maxResponseTimeMs: 1000
  scheduleEverySeconds: 60
  regions: [us-east-1, eu-west-1, ap-southeast-2]
  alert:
    severity: critical
    onFailure: page
```

### Synthetic → SLO
Synthetic availability over a window is a valid SLI:
```
synthetic_availability = successful_checks / total_checks
```
Use it for **customer-facing uptime** SLOs and for critical paths real-user traffic may miss.

### Synthetic alerting
- Failures → **Critical** page (see [Alerting & On-Call](./alerting-oncall.md)).
- Shelate/instance-level (flaky single region) → Warning, not page, to avoid alert fatigue.
- Avoid false positives: allow a configurable number of consecutive failures before paging.

## RUM / Frontend (UX) Analytics

RUM captures real browser telemetry: page loads, Web Vitals, JS errors, network requests, and user journeys — giving the **user-experience view** that server-side telemetry cannot.

### Standard RUM signals (Web Vitals)
| Metric | What it measures | Target (budget) |
|--------|------------------|-----------------|
| **LCP** (Largest Contentful Paint) | Perceived load speed | ≤ 2.5 s |
| **INP** (Interaction to Next Paint) | Responsiveness | ≤ 200 ms |
| **CLS** (Cumulative Layout Shift) | Visual stability | ≤ 0.1 |
| **FID** (First Input Delay) — older: pointer to INP | Input responsiveness | ≤ 100 ms |
| **TTFB** | Server response start | depends on stack |

### RUM events you should capture
- **Page load** (with Web Vitals)
- **Route/page view** (SPA navigation)
- **JS errors** (with stack + sourcemap)
- **Frontend → API latency & failures** (correlate to backend traces)
- **User interactions** / conversions (funnel analytics)

### RUM → backend correlation
- RUM session carries the **same `trace_id`** as the backend so you can jump from a slow page view to the server trace.
- Instrumentation: **OTel RUM SDK** (JS/browser) — keeps RUM vendor-neutral and correlates with server OTLP.

### Browser SDK principle
```html
<script src="https://unpkg.com/@opentelemetry/instrumentation@latest"></script>
```
Configure OTel RUM to export to the Collector via OTLP HTTP, set `service.name` (e.g., `web-app`), and attach session/user context.

## Frontend Metrics in the Observability Backend

| Concern | Standard |
|---------|----------|
| Frontend signals | Web Vitals + JS errors + route + API latency via OTel RUM → Collector |
| Backend correlation | `trace_id` shared between RUM and server traces |
| Dashboards | Web Vitals dashboard (LCP/INP/CLS by route, device, browser, region) |
| Performance budgets | Web Vitals budgeted; alert on regressions (not page on every dip) |
| Funnels / analytics | Conversion and step drop-off for key journeys |
| Deploy annotations | Overlaid on RUM performance charts |

## Operational Standards

| Practice | Requirement |
|----------|-------------|
| Coverage | ≥2 regions; one off-origin; API checks 1 min, browser 5–15 min |
| SLO | Synthetic availability is an SLI for uptime SLOs |
| Alerts | Failure → Critical page; flaky → Warning |
| Correlation | RUM shares `trace_id` with backend traces |
| Vitals | Capture LCP/INP/CLS; budgeted |
| Dashboards | Web Vitals + journeys dashboard; annotated on deploys |
| As code | Synthetic checks versioned in repo |

---

## Anti-Patterns

| Anti-Pattern | Problem | Solution |
|--------------|---------|----------|
| Synthetic-only | Misses real-user reality | Add RUM |
| RUM-only | No detection when traffic is light/zero | Add synthetic |
| Single-region checks | Blind to geography | ≥2 regions, off-origin |
| Page on flaky synthetic | Alert fatigue | Consecutive-failure threshold, dedupe |
| Vitals captured but not budgeted | No action | Performance budgets + alerts |
| RUM without trace correlation | Can't debug the backend | Share `trace_id` via OTel |
